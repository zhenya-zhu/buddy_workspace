## 1. 先定义用户变化，再定义页面和功能 [推断]

设计顺序：**一个可触达的人群 → 一个反复出现的场景 → 用户正在采用的替代方案 → 一个值得切换的结果 → 最小行为闭环 → 获客与付费实验 → 扩张**。

每个产品 Brief 必须能填完这句话：当【具体人群】遇到【具体情境】时，目前用【替代方案】，但受限于【代价/障碍】；我们帮助其完成【可观察任务】，通过【行为证据】决定是否继续投入。

不要把“全球用户”“AI 个性化”“SEO 流量”单独当作用户需求。全球是市场愿景，AI 是能力选项，SEO 是渠道；三者都需要服务于具体任务。

| 创业知识 | 本项目的用法 | 可审阅产物 | 检查方式 |
|---|---|---|---|
| Disciplined Entrepreneurship 的 beachhead [原文，S1] | 首先选可以用相似产品与销售过程服务的细分市场 | 首发用户、情境、渠道及排除范围 | 能否通过同一渠道接触同类用户，而非每人都要一套方案 |
| The Mom Test 的客户访谈方向 [原文，S2]；以下问题为 [推断] | 问最近一次发生什么、如何解决、付出什么 | 去标识访谈主题、替代方案与反例 | 不以“你会用吗”的正面回答作为需求已验证 |
| Running Lean / Lean Canvas [原文，S3] | 把商业模型写成假设，优先验证最危险者 | 一页假设表和本轮第一风险 | 当前实验失败会改变哪个实际决策 |
| Testing Business Ideas / Test Card [原文，S4] | 实验开始前固定假设、方法、指标和判断线 | 实验卡与复盘卡 | 结果出来后不能偷偷改成功定义 |
| Traction / Lean Analytics / Obviously Awesome [推断，创业项目讨论线索] | 分别审查渠道、阶段指标、替代方案下的差异化 | 渠道表、漏斗、定位一句话 | 不把所有框架变成必须全部填完的大文档 |

最后一行是结合此前创业项目讨论的应用建议；本次未逐章核验这三本书。先用前四种方法形成闭环，其余按具体瓶颈补充。

## 2. 产品 Phase 与工程 Milestone 分开 [推断]

这里的产品 Phase 0 指**投入完整产品前，验证最危险假设的探索期**，不是必须先开发复杂系统。它与 SEO Playbook 的 Phase 0–7、工程 M0–M7 是三个维度。

| 产品阶段 | 决策问题 | 最小工作 | 出口证据；缺失则待定 |
|---|---|---|---|
| Phase 0A 问题与切入 | 谁在什么时刻愿意改变现有行为？ | 候选细分市场、访谈、替代方案和搜索意图检查 | 重复出现的真实事件；有可触达招募渠道；写出反例与不服务谁 |
| Phase 0B 首次价值 | 用户能否理解并独立完成核心任务？ | 一个可点击/可操作流程，必要时人工交付 | 目标用户实际操作记录；关键卡点已修复；说得清获得什么 |
| Phase 0C 重复价值与付款 | 用户是否自愿回来、愿为可交付服务付款？ | 小批量 Concierge、真实交付、明确收费试验 | 分渠道队列数据、回访原因、履约工时、付款与退款记录 |
| Phase 1 Web MVP | 哪些已验证步骤值得自动化？ | 只自动化重复且明确的流程 | Web 能独立交付；安全/隐私/支持/发布门禁通过 |
| Phase 2 增长验证 | 哪个渠道能持续带来合适且会留存的用户？ | 小规模比较渠道，完善高价值内容 | 按来源观察激活、留存、付费及获客成本，不只看点击量 |
| Phase 3 扩张 | 扩人群、场景、国家、平台，哪个收益最大？ | 每轮只扩一个主要维度 | 新人群需求证据、增量成本、风险审核及继续/撤回条件 |

工程可提前做小型 PoC，不能因此宣布产品假设通过。健康内容审核与适用地区判断是并行的上线前置条件；未通过时仍可做不包含运动指导、不过度采集健康信息的需求与可用性研究。

## 3. Phase 0 的最小交付包 [推断]

先做下面六项，足够启动学习，不必一次完成整个平台：

1. **一页机会 Brief**：人群、情境、替代方案、价值主张、首发国家与语言、不能承诺什么。
2. **一张假设清单**：需求、首次价值、复用、付费、可交付性、安全/法规各一项；标明最大风险。
3. **一个核心体验原型**：有真实输入、可理解结果、返回/退出/错误状态；允许明确披露的人工服务。
4. **少量入口素材**：同一受众下先测试两种定位文案，第三种留作备选；不需要批量建设 SEO 页。
5. **一份实验卡**：对象、来源、主要指标及分母、护栏指标、时间窗口、预算、继续/调整/停止条件。
6. **一份复盘**：事实、解释、偏差、下一轮只改的 1–2 个假设。不得把观察推断为因果。

访谈可从 8–12 人开始，可用性可先做 5–8 人，这是节约成本的探索批次，不是行业达标线或统计保证。数量之外还要查看样本是否同质、是否存在明显反例、是否只招到了熟人。

## 4. 三类证据分别管理 [推断]

| 证据 | 能回答什么 | 不能代替什么 |
|---|---|---|
| 临床/内容依据 | 某方法在研究人群中的结果、限制和风险 | 消费者是否想用产品、普通用户能否正确执行 |
| 用户行为 | 能否完成、愿否复用、何时停止、愿否付费 | 临床疗效、疾病排除、动作机制 |
| 商业与交付 | 获客、收款、支持和审核成本是否可承受 | 产品安全性或监管许可 |

个人经历可以生成好问题；几位用户点赞只能提示方向；实际重复使用和付款提供商业证据。不同证据不能相互“升级”。

每条结论保留：来源、适用人群、观测周期、样本/分母、反例、已知偏差、状态（通过/不通过/待定）、下次复查时间。仓库仅放可公开汇总，不放健康记录、联系方式和支付资料。

## 5. 网站、Web 产品与原生 App 的分工 [推断]

- **内容/SEO 层**回答具体问题，独立提供价值；用户不点 CTA 也应有所收获。
- **转化实验层**快速比较价值主张与下一步是否明确，使用受控流量。
- **共享 Web 产品层**交付一次完整任务，保存用户主动选择继续的状态；初期可以很小。
- **App 层**在持续使用已被证明后，围绕提醒、快捷进入、离线等确切需求投入。

这些是职责边界，不要求四套系统或四个仓库。初期一个响应式网站加共享业务逻辑即可。用户从某个情境进入，应该接上对应任务，而不是被送回通用首页重新填写。

**建 App 的判断**：先记录用户在 Web 中为何无法复用；用现有提醒/入口做小实验；只有平台能力的增量收益足以承担开发、商店审核和维护成本时才立项。用户说“做个 App 吧”本身不够。

## 6. 增长与商业决策 [推断]

入口点击率适合发现文案问题，产品判断至少要继续看到**首次完成 → 到期返回 → 重复完成 → 付费与履约**。

- 按招募渠道与入组日期分队列；观察窗口未成熟的人单列，不能算流失。
- 不把不同关键词、国家、渠道的转化差异直接解释成文案 A/B 因果。
- 小样本先定位摩擦与动机；正式 A/B 才预先确定主要指标、最小有意义差异、样本量与结束规则。
- 付费测试必须可真实交付，提前清楚说明内容、期限、人工部分、退款；兴趣、候补、付款分别计数。
- 成本包含内容制作与专业审核、支持、支付费用、退款、获客和基础设施。托管便宜不代表服务经济性成立。
- SEO 的索引/排名积累与两周用户探索分别评价；不能等待自然流量才访谈，也不能由两周没排名断言需求不存在。

## 7. 每周产品评审：只做一个主要决策 [推断]

| 问题 | 必须交付 |
|---|---|
| 本周最危险的假设是什么？ | 一个假设和预先写明的判断线 |
| 得到了什么新证据？ | 原始记录的受控位置、去标识汇总、缺失与负面结果 |
| 瓶颈在哪里？ | 获客 / 理解 / 首次完成 / 重复使用 / 付费 / 履约，择主要一项 |
| 下周改什么？ | 1–2 项变化、负责人、预算上限和复盘日期 |
| 为什么现在值得写代码？ | 自动化将减少哪项已观察到的成本或摩擦 |

默认任务状态是待定。文档完成只证明设计已记录，不证明市场验证、医疗审核或上线完成。
