# 出海建站：前端技术架构约束规格 v1.0

> **这份文档的用途**：把哥飞（出海 SEO 建站方法论）内容里所有对「技术架构选型」构成约束的标准抽出来，整理成一份可交给第三方独立评审的规格。
> **评审者的任务**：判断给定架构能否以**更低的实现成本、更少的出错概率**满足全部 L0 约束；若存在更优解，指出它在本规格之外的额外收益。
> **不做什么**：不评价框架流行度、不讨论代码风格、不涉及视觉设计。

**来源**：哥飞公众号 826 篇（ima 知识库「哥飞公众号文章同步」），本规格引用其中技术相关条目。完整清单见 `~/.workbuddy/skills/gefei-web-checklist/`。

---

## 0. 给评审者的阅读说明

1. **先看第 2 节的 L0 条目**。L0 是架构锁：选错框架后无法通过配置弥补，只能重构。L0 全过 = 及格线。
2. **再看第 3 节排除清单**。已确认的失败形态，可直接用于否定方案。
3. **第 6 节是这份规格的空白区**。哥飞原文只讲「怎么做能被收录、能排名」，**没有**讲构建时长、单站复制成本、多语言扩展成本、运维负担。**"更好的架构"差异主要出现在这里**，请务必逐项回答。
4. **不要用"某框架也能做到"来论证通过**。判据是「默认行为是否满足」而非「是否可配置实现」。见第 7 节评分说明。

**标记约定**：
- `[原文]` = 哥飞文章有明确表述，可引用
- `[推断]` = 由多条原文推导，原文无直接表述
- `[工程]` = 通用工程约束，非哥飞观点，但会影响架构可行性

## 1. 约束分级

| 级别 | 定义 | 判定后果 |
|---|---|---|
| **L0 架构锁** | 选错技术路线后无法通过配置弥补，重构成本 > 重写 | 任一不过 → 架构不合格 |
| **L1 实现约束** | 任何架构都能满足，但存在典型错法；需架构层面预留机制 | 任一不过 → 可上线但有确定性风险 |
| **L2 运营支撑** | 架构必须能支撑的运营动作（巡检、迭代、灰度） | 缺失 → 站点无法长期运营 |

## 2. 约束条目

### TR-01 参与排名的正文必须在服务端输出的 HTML 里 `[L0] [原文]`

**要求**：搜索引擎请求 URL 后拿到的 HTML 必须含完整正文，不依赖客户端 JS 执行。

**依据**：
> "拿到一个网址后，程序发出一个 GET 请求，获取网址对应的 html 代码……**注意，这里只是获取到了 html 代码，并没有去执行 html 代码。**"（《如何制作出SEO友好的网页？》）

> "运行代码需要消耗额外的算力，谷歌只会给一些大网站有这样的优待……对于我们做的小破网站，谷歌不算浪费算力的。"

**典型错法**：CSR SPA（`useEffect` 里 fetch 数据）、Next.js 里 `'use client'` 包住整页、`client:only` 挂载的组件承载正文、静态壳 + 客户端注入列表。

**验证**：
```bash
curl -s https://example.com/target | grep -c "核心关键词"   # 必须 > 0
curl -s https://example.com/target | wc -c                  # 与渲染后 DOM 体积差 < 30%
```
外加：浏览器禁用 JS 后正文须完整可见；GSC「网址检查 → 已抓取的 HTML」须含正文。

**满足形态（不唯一）**：SSG、SSR、ISR、服务端模板渲染（Go/PHP/Python 模板）均可。

---

### TR-02 多语言必须是真实可独立收录的 URL `[L0] [原文]`

**要求**：语言切换改变 URL；每种语言有独立 TDH、独立 hreflang（含 `x-default`）、互相内链用 `<a href>`。

**依据**：
> "为什么多语言不能用 js 切换？因为 js 切换不会改变网址……只能抓取到一种语言的内容，也就只能参与一种语言的搜索排名。那么这个网页的多语言就相当于白做了。"

**前提约束**：语言版本用**子目录**（`/es/`）而非子域名。
> 依据：《再聊多语言：为什么不建议使用子域名而更建议使用子目录》——子目录继承主域权重。

**典型错法**：`react-i18next` / `vue-i18n` 运行时切语言、纯前端读取浏览器语言做跳转、用 `?lang=es` 参数但未做 canonical 区分。

**验证**：
1. 点语言切换 → URL 变化且为目录形式。
2. 每种语言 `<title>`/`<h1>` 是目标语言（不是英文复用）。
3. 各版本有自引用 canonical + 互指 hreflang。
4. `curl -s /ja/` 返回的是日文 HTML，不是英文 HTML + JS 翻译。

---

### TR-03 路由必须允许任意页面 3 次点击可达 `[L0] [原文]`

**要求**：任何页面从首页出发 ≤3 跳。URL 层级与导航层级要扁平化。

**依据**：
> "通常我们会说，页面深度不要超过 5 层，但哥飞建议，最好在 3 层内。也就是你要保证你网站的任何一个页面，都可以点击三次就能够到达。"

**对架构的含义**：
- 目标页应是 `/es/tool-name`（L1–L2），不能是 `/es/tools/image/avatar/edit/x`。
- 需要「全量索引页 + 页脚广度入口」作为兜底，把深层页面拉平（参考 Toolify 的页脚结构）。
- 内容集（CMS/Content Collections）需要能被一个索引页全量枚举——即架构要支持"全量列表渲染"而不只是分类浏览。

**验证**：Screaming Frog 爬全站，`Crawl Depth > 3` 的页面占比 = 0。

---

### TR-04 元数据必须逐页可控、且可在服务端生成 `[L1，SPA 下退化为 L0] [原文]`

**要求**：每页独立 Title / Description / H1，且不得重复。

**依据**：
> "TDH = Title + Description + H1"（《从 TDK 到 TDH》，Keywords 已淘汰）
> 每页 TD 不得重复（《谷歌喜欢的页面有哪些特征？》第 11 条）

**对架构的含义**：元数据生成必须与路由 1:1 绑定，由数据驱动（词表 → 页面 → TD），不能手工散写。100 页里手工写必有 20 页重复或漏写。
**典型错法**：SPA 全局 `document.title` 拼接；多语言复用英文描述。

**验证**：全站抓取后统计 TD 重复率 = 0；每种语言 TD 为对应语言。

---

### TR-05 首页「最新内容」模块 + 全量索引页 `[L1] [原文]`

**要求**：首页有一个随内容更新的列表模块，**只输出标题 + 链接**（真实 `<a href>`）；另有一个全量索引页（`/all` 或 `/sitemap` 页面）可从页脚一级进入。

**依据**：
> "甚至哥飞目前最新的这个网站不到一个月收录十几万，压根就没有 Sitemap。方法就是在首页不断的列出最新的内容，同时有一个页面能够一页一页列出网站所有页面。"

**对架构的含义**：纯静态站若首页不重建，这个模块就是死的。**架构必须解决"新增页面后首页与索引页如何更新"**——ISR / 按需重建 / 构建钩子，三选一。

**验证**：间隔 24 小时抓两次首页，列表内容有变化；DOM 中为 `<a>` 而非 JS 点击。

---

### TR-06 首页正文不得被内页内容撑大 `[L1] [原文·红线]`

**要求**：首页列表模块**只放标题和链接，禁止服务端输出内页正文/问答全文**。

**依据**（唯一有完整事故复盘的坑）：
> 首页原本约 400 词，某次发版后"最新问答列表模块把问题和回答全文都在首页输出了"，首页变成两三千词。"核心关键词的密度下降了。并且谷歌是懂语义分析的……跟 GPT 4o 没多大关系了。于是谷歌的惩罚就来了"——**下掉模块后仍未短期恢复**。

**对架构的含义**：列表组件与正文组件必须解耦，列表页模板不得复用详情页内容组件。这是模板层的强制边界，不是内容规范。

**验证**：`curl` 首页，正文词数与核心词密度；首页 DOM 的列表区域内不得出现 `<p>` 长文本。
**阈值**：首页正文 ≤500 词（工具型站不设下限，见备注）、核心词密度 ≥1%、80% 以上内容与核心需求相关。
> **备注（反例，防误读）**：`blackscreen.app` 整站 40 个单词、年 1000 万访问、拿下该词第一。**词数不是门槛，需求满足度才是。** 本条防的是"语义跑偏"，不是"字数不够"。

---

### TR-07 工具页必须有服务端输出的说明正文 ≥200 词 `[L1] [原文·红线]`

**要求**：纯工具界面（只有输入框和按钮）不合格；每页须有解释"是什么/解决什么/怎么用/限制/FAQ"的正文。

**依据**：
> "你不做内容，谷歌怎么知道你的工具到底有什么用，谷歌不可能去运行你的工具来判断你的工具的用途，所以只能根据你写的内容来判断。"

**对架构的含义**：工具页模板必须为"功能区 + 说明区 + FAQ 区 + 案例区 + 内链区"五段式，功能区可 JS 化（island），**说明区必须静态文本**。若架构把工具页做成纯 SPA 应用容器，此条无法满足。

**验证**：禁用 JS 后每页仍有 ≥200 词说明性正文（不含按钮文案）。

---

### TR-08 重复交互文案不得污染正文词频 `[L1] [原文]`

**要求**：核心关键词须是页面纯文本词频第 1，密度 ≥1%；"Generate/Download/Copy"这类功能词不得高频出现于正文语义区。

**依据**：《如何不让你网页里的大量重复按钮文案干扰你页面关键词密度？》——重复文案占用词频、挤占核心词权重（与 TR-06 同一病理）。

**对架构的含义**：DOM 需要有**语义分区**——交互控件区与说明正文区分离，使正文词频可独立统计；组件化时不能把按钮文案与说明文案塞进同一文本容器。

**验证**：抓纯文本做词频 Top20，核心词排第 1。

---

### TR-09 URL 一旦有排名不得随意变更 `[L1] [原文]`

**要求**：`[原文]`《页面已出词后，慎改 Title 与 H1》。架构含义：**URL 与 slug 必须由稳定主键生成**，不能由标题自动生成（改标题 → URL 变 → 权重归零）。如确需改，必须有 301 映射表机制。

**验证**：标题变更后 URL 不变；存在 301 规则文件或中间件。

---

### TR-10 渲染模式必须匹配页面规模 `[L0] [原文+工程]`

**要求**：页面数量决定渲染模式，不能一套模式通吃。

**依据**：
> `[原文]` 程序化 SEO"实际不是生成静态文件，而是用动态页面，根据不同的 url 路径参数显示不同的页面"（1600 万颜色页的例子）。

**分界（`[工程]` 推断，需评审者校准）**：
| 页面规模 | 可行模式 | 不可行 |
|---|---|---|
| < 5,000 | 全量静态构建 | — |
| 5,000–50,000 | 静态 + 增量/分片构建 | 每次全量 rebuild |
| > 50,000 | 按需渲染（SSR/ISR）+ 分层 sitemap + 缓存策略 | 全量静态构建 |

**对架构的含义**：如果计划"先做小站再扩到十万页"，架构必须**一开始就支持切换渲染模式**，否则扩量时等于重写。这是本规格中**最容易被低估的一条**。

---

### TR-11 页面发布必须可控速（新站首周 ≤20 页）`[L1，架构影响大] [原文·红线]`

**要求**：新域名上线首周可访问 URL ≤20 个（程序化 SEO 在**老域名**上不受此限）。

**依据**：《新站批量化上页面，必死》——一堆无内链、无用户行为数据、无竞争力的页面同时出现，易被判低质。

**对架构的含义**：静态站"一次构建 = 全站上线"的默认行为**直接违反此条**。架构必须提供**发布开关**（如数据表 `status: draft/published` 参与构建过滤），否则无法分批放量。

**验证**：上线首周 `site:` 收录的 URL 数 ≤20，且全部在内链体系内（无孤岛页）。

---

### TR-12 一套代码支持多域名多站 `[L1] [原文]`

**要求**：一个关键词一个域名（AR-01）。同时原文认可"模板化批量上站"——同一套程序今天做 AI 贴纸站、明天做 AI 头像站。

**依据**：
> "一个关键词一个域名，一个域名一个功能，一个功能一个主页，这样 SEO 权重高。"
> 内容型 AI 站的成本优势："同一套程序，今天上 AI 贴纸站，明天上 AI 头像站、AI 视频站"。

**对架构的含义**：这是**多租户 vs 每站独立仓库**的抉择点。评审时须回答：第 2、3、4 个站上线时，需要复制多少东西？（建议比较：配置量、构建流水线复用率、共用组件比例）

---

### TR-13 场景页必须能数据驱动批量扩展 `[L1] [原文]`

**要求**：主大词下至少 3–5 个**场景页**，每页有该场景专属的模板/默认参数/案例，不是换标题的同一页。

**依据**（deepai 复盘）：`text2img` 页 230 万 → 73 万，`chat` 页 110 万 → 60 万，但 `chat/gpt-chat` 54.5 万 → **220 万**。原因："对话类需求在一个页面里就比较容易完成……图片类不一样。头像、Logo、产品图、营销海报、社媒配图，每一种需求对页面结构、默认参数、模板、案例、编辑能力、下载能力的要求都不同。"

**对架构的含义**：场景必须是一行数据（配置），不是一份模板文件。新增 20 个场景 = 加 20 行配置 + 0 个新页面文件。若每个场景要复制一份 `.astro`/`.tsx`，架构不满足。

**验证**：新增一个场景页的改动量（文件数、行数）≤ 一个配置文件条目。

---

### TR-14 模型调用与密钥必须在服务端 `[L0，安全+成本] [工程]`

**要求**：`[工程]` AI 站的模型 API key 不得出现在客户端产物中；调用经服务端接口代理，支持流式响应。
**为什么是 L0**：key 泄露 = 成本不可控 + 账号封禁，且无法通过前端配置修复。
**验证**：`grep` 构建产物中是否含 key 前缀；Network 面板确认无第三方模型域名直连。

---

### TR-15 静态资源与验证文件可放根目录 `[L1] [原文+工程]`

**要求**：`robots.txt`、`sitemap.xml`、`ads.txt`、`favicon` 均可部署到域名根目录且返回 200。

**依据**：
- `[原文]` 多语言 robots.txt 须正确拦截参数页/搜索结果页（《多语言网站 robots.txt 设置指南》）
- `[原文]` AdSense 审核"代码段与 ads.txt **两者都要做**，不是二选一"
- `[原文]` Sitemap 是"建议"不是命令，但小站仍需 GSC 提交

**验证**：`curl -I` 四个路径均 200，`Content-Type` 正确；`robots.txt` 无 `Disallow: /`。

---

### TR-16 关键指标可按页面归因 `[L2] [工程]`

**要求**：能按 URL 获取曝光/点击/排名/停留，且能区分语言版本与场景页；能跑周度巡检（`site:`、收录数、抓取频率、曝光跌幅）。

**依据**：`[原文]` GSC 四级信号判断是否被惩罚；`site:` + Past hour 判断爬虫频率。
**对架构的含义**：URL 规范必须统一（多语言目录、场景页独立 URL），否则数据无法聚合，GSC 四象限处置（改 TD / 改页面 / 重拆场景）无法执行。

## 3. 已确认不满足的形态（可直接用于否定方案）

| 形态 | 违反条目 | 说明 |
|---|---|---|
| Vite + React Router / CRA 纯 CSR | TR-01 | 源码 HTML 为空壳 |
| 任意 SPA + 预渲染插件但只覆盖首页 | TR-01 | 内页仍是空壳 |
| `react-i18next` 运行时切语言 | TR-02 | URL 不变，只有默认语言被收录 |
| Next.js 全站 `'use client'` | TR-01 | 编译通过、浏览器正常、SEO 全废 |
| Astro 用 `client:only` 渲染正文组件 | TR-01 | 该组件内容不在 HTML 中 |
| 纯静态站 + 无重建机制 | TR-05 | 首页"最新内容"不更新 |
| 全站静态构建 + 一次性上线所有页面 | TR-11 | 无法分批放量，违反新站红线 |
| 每个场景一个模板文件 | TR-13 | 场景扩展成本线性增长 |
| 前端直连模型 API | TR-14 | key 泄露 |
| 多层分类目录（`/tools/a/b/c/d`） | TR-03 | 深度超 3 |

> 注意：**"某框架也能做到"不等于"该框架默认满足"**。例如 Next.js 可满足 TR-01，但其默认路由组件的写法极易退化为 CSR；Astro 默认满足 TR-01，但用错指令同样退化。评审时请按"团队最可能写出的默认实现"评分，而不是按"理论上限"。

## 4. 三种站型的最低要求

| 要求 | 内容站 | 工具站 | AI 工具站（含内容型 UGC） |
|---|---|---|---|
| TR-01 服务端正文 | 必须 | 必须（说明区） | 必须（说明区 + UGC 页） |
| TR-02 多语言目录 | 常做 | 常做 | 常做 |
| TR-05 首页最新 + 索引页 | 必须 | 必须 | 必须（UGC 需索引页） |
| TR-07 工具页 ≥200 词 | — | 必须 | 必须 |
| TR-10 渲染模式可升级 | 需要 | 需要 | **必须**（UGC 无上限） |
| TR-11 分批发布 | 必须 | 必须 | 必须 |
| TR-13 场景数据化 | 一般 | 一般 | **必须** |
| TR-14 服务端密钥 | — | 视功能 | **必须** |

## 5. 评审问卷（请逐条回答，不要合并）

对每个候选架构，按以下格式输出：

| 条目 | 该架构如何满足 | 是否默认满足 | 实现成本 | 残留风险 |
|---|---|---|---|---|
| TR-01 | | 是 / 需配置 / 需自研 | 低/中/高 | |
| … | | | | |

并**必须单独回答**以下 6 个问题（这些是哥飞原文的技术分界点，也是最容易分歧的地方）：

1. **新增 1 个语种，需要改多少东西？**（路由、TD、hreflang、内容、sitemap 各要动哪里）
2. **从 100 页扩到 50,000 页，架构要不要重写？** 构建时长是多少？
3. **首周只想上 15 个页面，其余 500 页待放量，怎么实现？**（是否只需改数据标记）
4. **首页"最新内容"模块，在内容更新后多久生效？**（需要全站重建吗）
5. **新增 1 个 AI 场景页（不同默认参数、不同模板、不同案例），改动量是多少？**
6. **第 2 个站上线，能复用多少？**（代码、构建流程、内容结构）

## 6. 本规格的空白区（原文未覆盖，是"更好架构"的差异来源）

哥飞的方法论只解决"能不能被收录、能不能排名"。以下维度**原文没有标准**，属工程判断，请评审者补充对比：

| 维度 | 为什么重要 | 建议比较方式 |
|---|---|---|
| **构建时长** | 静态站扩量后每次发布要等多久 | 1,000 / 10,000 页的实测 build time |
| **单站复制成本** | 一站一域名，做第 N 个站的边际成本 | 新站初始化所需步骤数 |
| **多语言扩展成本** | 翻译 8 个语种时的工作量 | 每语种改动文件数 |
| **无 JS 退化程度** | 工具功能本身是否需要 JS | 禁用 JS 后可用功能占比 |
| **运维负担** | 是否需自维护服务器/数据库 | 托管方式、SLA、月成本 |
| **缓存与 TTFB** | 加载速度是谷歌喜欢页面的第一条特征 | 冷启动 TTFB、CDN 命中率 |
| **可回滚性** | 改首页出事故（TR-06）后能否快速回滚 | 回滚耗时、是否有版本化部署 |
| **内容差异化能力** | 程序化页面易被判重复 | 模板内可插入的差异化字段数 |

## 7. 评分与放行标准

- **L0 全过（TR-01/02/03/10/14）** = 架构及格，可进入实现。
- **L1 全过（其余）** = 可上线。
- **任一 L0 不过** = 无论其他项多好，判定不合格。
- **"需自研才能满足"记半分**：自研意味着长期维护成本，且违反默认行为原则。
- 若两个方案 L0/L1 均全过，**用第 6 节的实测数据比较**，不要用框架偏好比较。

**判定示例**：一个"功能强、生态好、但需要手写 SSR 配置且默认构建产物为空壳"的方案，在 TR-01 上应记为「需配置」而非「满足」——因为团队只要漏一处 `'use client'`，就产生一个不会被收录的页面，而这类错误在浏览器里看不出来。
