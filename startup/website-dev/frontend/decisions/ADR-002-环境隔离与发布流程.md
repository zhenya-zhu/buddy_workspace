# ADR-002：环境隔离、域名与发布流程

> 状态：建议采纳，待首站配置和部署验证 [工程]  
> 日期：2026-10-26  
> 相关：[ADR-001 Astro 多站架构](./ADR-001-astro-多站点架构.md)、[技术架构约束](../tech-architecture-spec.md)

## 决策

**每站点使用 local、PR preview（可选）、staging、production；共享代码，隔离部署与数据。** 初期使用 GitHub Actions + Wrangler，不自研发布后台；production 需要批准。代码部署与内容发布分开建模，初期 Git 内容可以随代码一起发布。

| 环境 | 样例 | 发布来源 | 可访问性 | 数据 |
|---|---|---|---|---|
| local | localhost:4321 | 开发者命令 | 本地 | local/test |
| preview | GitHub PR 临时 Workers URL | PR CI（可选） | 尽量受控 | 测试 |
| staging | staging.site-a.com | main 合并自动部署 | Cloudflare Access 限制访问 | staging DB/Secrets |
| production | site-a.com | 经过批准的 Git SHA 发布 | 公开 | production DB/Secrets |

各站点独立 Worker：site-a-staging、site-a-production；第二个站增加 site-b-staging、site-b-production。**不因一代码库而默认共用运行中的多租户 Worker**。生产网站域名与 staging 子域名通过配置管理，不应硬编码进通用页面模板。

## 关键规范与可验证规则

| ID | 要求 | 验证 |
|---|---|---|
| DEP-01 | 部署标识唯一由 site_id + environment + git_sha/release_id 确定 | 日志/CI artifact 记录全部字段 |
| DEP-02 | staging/prod 使用不同 Worker、Secrets、D1/R2 namespace 和可区分的缓存 key | 检查绑定；staging 写入无法被 prod 读取 |
| DEP-03 | 所有正式站点域名都从 site config + environment config 获取 | 查看原始 HTML 的绝对 URL |
| DEP-04 | staging、preview 不可被搜索引擎索引 | Cloudflare Access 认证 + X-Robots-Tag: noindex；生产没有 noindex |
| DEP-05 | staging 不提交 GSC 站点地图；production sitemap 仅含已发布正式 URL | 请求并检查 sitemap XML |
| DEP-06 | Staging 成功后才允许 Production 审批；生产使用明确 SHA，禁止浮动引用 | GitHub Actions 运行记录 |
| DEP-07 | deploy 后自动 smoke test：200/404、HTML、canonical、hreflang、robots、sitemap、AI API | CI 失败即阻断/报警 |
| DEP-08 | 部署失败可以回滚 Worker 版本；内容可回滚其发布版本 | 演练并记录 |
| DEP-09 | schema 变更使用向后兼容的 expand/migrate/contract，代码回滚不假设 DB 自动回滚 | migration review |
| DEP-10 | Secrets 由环境管理；测试/生产 AI Key、限流与成本配额独立 | 客户端 bundle 检查及权限测试 |

**SEO 特别注意**：[工程] robots.txt 的 Disallow 不能作为防止 staging 收录的唯一手段；采用 Access 或 HTTP noindex。noindex 必须允许爬虫访问到响应才可被看到，所以受 Access 保护是更可靠的隔离手段。生产绝不能意外返回 noindex。参考：<https://developers.google.com/search/docs/crawling-indexing/block-indexing>。

## 代码发布 Pipeline

```text
Feature branch -> Pull request -> CI (typecheck, tests, build, SEO checks)
                                         |
                                      Merge main
                                         |
                                 Auto deploy staging
                                         |
                                 Staging smoke / QA
                                         |
                         GitHub Environment approval
                                         |
                    Deploy exactly verified commit SHA to prod
                                         |
                                Prod smoke / metrics
                                         |
                           Roll back Worker if necessary
```

建议 CI 在 staging 后固定产出构建产物/构建清单，在生产部署**同一已验证 SHA**；如果因不同环境变量必须重新构建，需在流水线记录 artifact/hash 与环境差异，不能默认相同 SHA 就一定生成完全相同 HTML。

正式环境的发布权限由 GitHub Environments 保护，密钥交给 Cloudflare/GitHub 的适当 Secret 管理。配置以 Wrangler environments 为起点（bindings/vars 并不应假定自动继承），Cloudflare 文档：<https://developers.cloudflare.com/workers/wrangler/environments/>。

## 内容发布 Pipeline

```text
Draft -> Review -> Approved -> Publish selected ContentRevision
                                  |
                   Update production published pointer
                                  |
                  Invalidate affected CDN pages/index/sitemap
                                  |
                          Verify public HTML
```

对于 Git Markdown MVP，发布可随部署进行，但仍应有公开内容清单和 draft 过滤。需要频繁发布、UGC 或 50k+ 页面时，引入 DB 内容修订版和独立发布操作。内容审核成功不意味着发布成功，更新数据库后还需刷新/等待缓存，并验证正式 URL 的 HTML。

**代码回滚 != 内容回滚 != DB rollback**。Worker 原生支持版本回滚，但数据库迁移可能不可逆，内容修订也应单独恢复。Cloudflare 文档：<https://developers.cloudflare.com/workers/configuration/versions-and-deployments/rollback/>.

## 部署参数契约（示意，非可直接复制运行的 Wrangler 配置）

```yaml
site_id: site-a
environment: staging
domain: staging.site-a.com
worker_name: site-a-staging
database_binding: DB_STAGING
storage_namespace: R2_STAGING
indexable: false
release_sha: <verified-git-sha>
```

不写死 Astro Adapter 生成的 Worker 入口；Wrangler `main`、`assets` 和 build 产物结构必须由实际 Astro/Adapter 版本生成并在 PoC 中核验。静态预渲染时，`SITE_URL`/canonical 可能在**构建时**固定，不能仅靠运行时切换环境变量。SSR 页面可通过可信站点配置选择 URL，但不应无条件相信请求 Host 头。

## 待实施的验收任务

1. 建立一个测试站点和 staging/prod Workers，自定义域名、独立绑定与 Access。
2. 在 GitHub Actions 中实现 CI -> staging -> approval -> prod，确认只能发布指定 SHA。
3. 构造 /、/es/、/tool、404、draft、sitemap 和 robots 的端到端测试；确认两环境返回正确 URL、canonical、hreflang。
4. 用测试文章演练状态放量、缓存失效与内容回滚。
5. 演练一次 Worker 发布回滚及一次兼容数据库迁移。
6. 记录部署时间、运行成本、冷/热 TTFB、生产 HTML 缓存行为和实际回滚时间。
